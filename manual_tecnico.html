4. Introducción y Resumen de las Tecnologías Utilizadas

4.1. Finalidad del Manual Técnico

El propósito primordial de este manual es constituir la referencia arquitectónica y técnica definitiva para la puesta en marcha, administración de infraestructura, despliegue, configuración de bases de datos, aprovisionamiento de servicios de backend y mantenimiento evolutivo del Sistema web para la gestión integral de trazabilidad y control de inventarios en plantas de productos perecederos bajo cadena de frío, concebido e implementado para la empresa AMATI HIELO.

4.2. Importancia de la Documentación Técnica para la Mantenibilidad

En el ciclo de vida del software comercial e industrial, los costos y esfuerzos asociados a la fase de mantenimiento superan frecuentemente el 70% del costo total de propiedad (TCO). En empresas con requerimientos de alta disponibilidad como plantas de hielo purificado, donde la interrupción de despacho de producto en frío genera mermas irreversibles e incumplimiento comercial, contar con una documentación exhaustiva de esquemas relacionales, flujos de autenticación desacoplados, contratos de API REST y variables de entorno minimiza la deuda técnica, elimina la dependencia de programadores específicos y asegura la continuidad operativa.

4.3. Alcance y Perfil del Lector Objetivo

El alcance comprende la totalidad de los módulos de software implementados en el repositorio: control de autenticación y seguridad por roles, administración de usuarios y catálogo geográfico, inventarios con control de entradas, salidas, mermas por lote y auditoría física ciega con conciliación de stock, recetas de producción con lista de materiales (BOM) para deducción en punto de venta (POS), punto de venta con arqueos semanales de caja, módulo predictivo de demanda asistido por variables climáticas y asistente conversacional basado en modelos de lenguaje natural (LLM).

Perfil del lector objetivo: Ingenieros de software, desarrolladores full-stack, administradores de bases de datos (DBA), ingenieros de infraestructura / DevOps y personal técnico responsable de la gobernanza de TI de AMATI HIELO o evaluadores universitarios de graduación.

4.4. Resumen Técnico del Sistema AMATI HIELO

AMATI HIELO opera una arquitectura desacoplada en tres niveles principales:

  • Capa de Presentación (Frontend): Single Page Application (SPA) construida en React 19 sobre el empaquetador ultrarrápido Vite 7, estructurada bajo componentes funcionales y utilidades CSS mediante Tailwind CSS. Incluye interfaces reactivas para inventarios, POS con teclado numérico, visualización de predicciones con gráficos de Recharts y un asistente chatbot embebido.
  • Capa de Servicios y Lógica de Negocio (Backend): Servidor RESTful desarrollado en Node.js 22 utilizando Express 4.21 en estándar de módulos nativos ECMAScript (ES Modules). Administra los flujos de autenticación, verificación de permisos mediante middlewares autoritativos, cálculo de costos unitarios de insumos, auditorías de inventario y canalización segura de solicitudes hacia servicios de inteligencia artificial.
  • Capa de Persistencia y Gobernanza de Datos (Base de Datos): Instancia PostgreSQL relacional gestionada en Supabase Cloud. Aloja más de 30 tablas relacionales, catálogos paramétricos, llaves foráneas con integridad referencial, índices optimizados y funciones almacenadas (RPC) con bloqueos atómicos por fila (FOR UPDATE) para evitar condiciones de carrera en el stock de inventario.

6.2. Fichas Técnicas por Tecnología Principal

1. React 19.2.0

  • Propósito dentro de la arquitectura: Núcleo del frontend para construir interfaces de usuario interactivas mediante el patrón de componentes jerárquicos basados en funciones y hooks (useState, useEffect, useMemo, useTheme).
  • Componentes dependientes: Todas las vistas en src/components/modules/ (Inventarios, Usuarios, Recetas, POS, Auditoría, Reportes, Dashboard).
  • Requisitos de compatibilidad: Node.js >= 18 para la etapa de construcción; navegadores con soporte ECMAScript 2020+ para ejecución cliente.
  • Consideraciones de actualización: Al actualizar versiones mayores de React, debe validarse la compatibilidad con recharts y librerías auxiliares que usen contextos de React DOM.

2. Express 4.21.2

  • Propósito dentro de la arquitectura: Servidor HTTP RESTful estructurado como capa intermedia de seguridad y lógica de negocio. Desacopla la base de datos de los navegadores clientes, centralizando la autorización de roles.
  • Componentes dependientes: Todos los controladores en backend/src/controllers/, middlewares requireSession y requireAdmin.
  • Requisitos de compatibilidad: Node.js v18.0.0 o superior con flag "type": "module" en package.json.
  • Consideraciones de actualización: Migraciones hacia Express v5 requerirán revisar el manejo de promesas asíncronas en controladores donde no se use bloque try/catch manual.

3. Supabase & PostgreSQL 15+

  • Propósito dentro de la arquitectura: Persistencia transaccional de datos y gestión de usuarios (esquema auth.users y public.perfil). Ejecución de transacciones complejas mediante RPC.
  • Componentes dependientes: Modelos y servicios del backend a través de supabaseAdmin.js y sincronización cliente.
  • Requisitos de compatibilidad: Acceso a Internet vía HTTPS (puerto 443) y compatibilidad con estándar de conexión de Supabase JS v2.
  • Consideraciones de actualización: Las extensiones y versiones mayores de PostgreSQL en Supabase se actualizan desde la consola web; las migraciones de esquemas deben ser rigurosamente idempotentes.

4. Google Generative AI SDK (@google/generative-ai 0.24.1)

  • Propósito dentro de la arquitectura: Interfaz de comunicación con los modelos de lenguaje Gemini (gemini-3.6-flash o fallbacks) para procesar consultas de usuarios con contexto de inventario en tiempo real.
  • Componentes dependientes: backend/src/services/geminiService.js, chatbotController.js y componente flotante Chatbot.jsx.
  • Requisitos de compatibilidad: Llave de API válida (GEMINI_API_KEY) con cuotas de uso habilitadas en Google AI Studio o Cloud Console.
  • Consideraciones de actualización: Supervisar la deprecación de identificadores de modelos (por ejemplo, transición de nombres de modelos experimentales a estables).

10.1. Arquitectura de Datos y Motor Relacional

El sistema implementa un motor relacional PostgreSQL 15+ hospedado en la plataforma de servicios en la nube de Supabase. 10.5. Procedimientos Almacenados y Funciones RPC Atómicas

El sistema delega las operaciones críticas de concurrencia al motor de base de datos a través de funciones almacenadas en PL/pgSQL. El procedimiento más relevante es registrar_movimiento_inventario: 

CREATE OR REPLACE FUNCTION public.registrar_movimiento_inventario(
  p_producto_id BIGINT,
  p_tipo TEXT,
  p_cantidad NUMERIC,
  p_motivo TEXT DEFAULT NULL,
  p_usuario TEXT DEFAULT NULL
)
RETURNS public.movimiento_inventario
LANGUAGE plpgsql
AS $$
DECLARE
  v_producto public.producto%ROWTYPE;
  v_movimiento public.movimiento_inventario%ROWTYPE;
  v_delta NUMERIC(12,2);
BEGIN
  -- 1. Validaciones preventivas de entrada
  IF p_producto_id IS NULL THEN RAISE EXCEPTION 'El producto es obligatorio.'; END IF;
  IF p_cantidad IS NULL OR p_cantidad <= 0 THEN RAISE EXCEPTION 'La cantidad debe ser mayor a 0.'; END IF;

  -- 2. Bloqueo exclusivo de fila (FOR UPDATE) para prevenir condiciones de carrera
  SELECT * INTO v_producto FROM public.producto WHERE id = p_producto_id FOR UPDATE;
  IF NOT FOUND THEN RAISE EXCEPTION 'No se encontró el producto seleccionado.'; END IF;

  -- 3. Determinación de la dirección del flujo de existencias
  CASE btrim(p_tipo)
    WHEN 'Entrada' THEN v_delta := p_cantidad;
    WHEN 'Salida'  THEN v_delta := -p_cantidad;
    WHEN 'Merma'   THEN v_delta := -p_cantidad;
    WHEN 'Ajuste'  THEN v_delta := p_cantidad;
    ELSE RAISE EXCEPTION 'Tipo de movimiento inválido.';
  END CASE;

  -- 4. Salvaguarda estricta de no negatividad de existencias
  IF v_producto.stock + v_delta < 0 THEN
    RAISE EXCEPTION 'El stock no puede quedar negativo. Existencia actual: %, intento de salida: %', v_producto.stock, p_cantidad;
  END IF;

  -- 5. Actualización atómica de existencias y registro en el Kardex
  UPDATE public.producto SET stock = stock + v_delta, updated_at = now() WHERE id = p_producto_id;

  INSERT INTO public.movimiento_inventario (producto_id, tipo, cantidad, motivo, usuario)
  VALUES (p_producto_id, p_tipo, p_cantidad, p_motivo, p_usuario)
  RETURNING * INTO v_movimiento;

  RETURN v_movimiento;
END;
$$;

11.1. Arquitectura del Backend en Capas

El backend de AMATI HIELO es una aplicación en Node.js construida sobre el framework Express 4.21, estructurada bajo una arquitectura por capas desacopladas:

  • Capa de Enrutamiento (src/routes/): Define los puntos de contacto HTTP RESTful, aplica middlewares de autenticación previa y mapea verbos (GET, POST, PUT, DELETE) hacia sus controladores correspondientes.
  • Capa de Controladores (src/controllers/): Valida los datos recibidos en el cuerpo (body) y parámetros de la solicitud, maneja excepciones y orquesta las respuestas JSON con códigos de estado HTTP semánticos (200, 201, 400, 401, 403, 404, 500).

  • Capa de Servicios e Integración (src/services/): Administra la comunicación con APIs externas como Google Gemini y consolida las estructuras de datos de auditoría e inventario.

11.7. Políticas de Seguridad, CORS y Middlewares Críticos

  • Verificación en Tiempo Real de Usuario Activo: El middleware requireSession no confía únicamente en la firma del token JWT; consulta en cada petición la tabla perfil. Si un colaborador es marcado como "Inactivo" por un administrador, su sesión es revocada de forma inmediata devolviendo un código 403 Forbidden.
  • Protección de Endpoints Sensibles: El middleware requireAdmin restringe las operaciones de creación de usuarios, alteración de recetas, modificación de proveedores y eliminación de auditorías a los roles Superusuario y Administrador.
  • Control de Orígenes Cruzados (CORS): Implementado en server.js mediante una función de filtrado dinámico que admite localhost, redes privadas locales (192.168.x.x, 10.x.x.x) y los dominios de producción registrados en FRONTEND_URL.
  • Límites de Payload: El parseador de cuerpos JSON está limitado a 8mb (express.json({ limit: '8mb' })) para permitir la carga segura de comprobantes de compras o firmas de auditoría sin vulnerabilidades de Denegación de Servicio (DoS).

12. Configuración e Implementación del Frontend

12.1. Arquitectura de la Interfaz de Usuario (React 19 SPA)

La aplicación cliente de AMATI HIELO está concebida como una Single Page Application (SPA) altamente responsiva, optimizada para terminales de punto de venta táctiles, escritorios de supervisión y dispositivos móviles de operarios en bodega.

  • Enrutamiento Protegido (App.jsx): Utiliza react-router-dom para gestionar rutas declarativas. Las vistas internas como /dashboard están envueltas en el componente ProtectedRoute, el cual verifica la presencia de credenciales activas antes de renderizar la aplicación.
  • Shell Principal (Dashboard.jsx): Centraliza la navegación a través de un menú lateral (sidebar) plegable, control de acceso por roles visual (deshabilitando opciones a operarios), métricas del día en tiempo real y selector de tema claro/oscuro.
  • Gestión de Notificaciones (Sonner): Provee retroalimentación visual no invasiva ante el éxito de transacciones de inventario, errores de conexión o avisos de stock bajo.
  • Visualización de Datos (Recharts): Genera gráficos interactivos de barras y líneas para el pronóstico de demanda semanal y comparación de tendencias de venta en relación con temperaturas climáticas.

12.2. Requisitos Previos

Para generar el compilado estático optimizado y minificado de producción:

Este comando ejecuta Rollup y genera el directorio dist/, el cual contiene archivos HTML, CSS purgado y JavaScript optimizado listos para desplegarse en cualquier servidor web estático.

Configuración de Nginx para enrutamiento SPA:

server {
    listen 80;
    server_name erp.amati.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name erp.amati.com;

    ssl_certificate /etc/letsencrypt/live/erp.amati.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/erp.amati.com/privkey.pem;

    root /var/www/amati-hielo/dist;
    index index.html;

    location / {
        # Esencial para evitar errores 404 al recargar rutas en React Router
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_cache_bypass $http_upgrade;
    }
}

12.7. Protocolo de Integración Frontend-Backend

Cada llamada realizada por los módulos de cliente a través de los servicios en src/services/ (por ejemplo, inventarioService.js) implementa la función utilitaria request(), la cual extrae de forma transparente el token de sesión almacenado (vía getAccessToken()) e inyecta el encabezado estándar: 

Authorization: Bearer [TOKEN_JWT_DEL_USUARIO]

12.8. Guía de Verificación Funcional Módulo por Módulo

Módulo Comprobación Funcional Clave Resultado Esperado Comprobado
Autenticación Ingreso con credenciales válidas e inválidas en /. Redirección a /dashboard con credenciales correctas; mensaje de error semántico ante claves erróneas.
Seguridad y Acceso Creación de nuevo usuario y cambio de estado a Inactivo. El usuario inactivo no puede iniciar sesión; el sistema impide auto-desactivarse o auto-eliminarse.
Inventarios Registro de entrada de insumos y mermas por merma física. Aumento o disminución inmediata en el Kardex; bloqueo de operaciones si el stock resultante fuese menor a cero.
Auditoría de Almacén Apertura de proceso, registro de conteo físico y cierre. Cálculo automático de varianza económica; ajuste atómico del stock si el administrador aprueba las diferencias.
Punto de Venta (POS) Generación de ticket de venta con producto BOM. Impresión del comprobante, aumento en ingresos diarios y deducción simultánea de ingredientes en inventario.
Arqueo de Caja Cierre y balance semanal de caja chica y terminal. Totalización de efectivo contra transferencias y bloqueo del periodo auditado para evitar duplicaciones.
IA Predictiva Consulta de proyección semanal y factores climáticos. Presentación de curva de demanda sugerida basada en temperatura y disponibilidad de insumos en bodega.
Asistente Chatbot Consulta de existencias críticas al botón flotante. Respuesta directa de 4 a 6 líneas con datos de stock reales de la base de datos en formato legible.

13. Verificación Técnica Final del Sistema

13.1. Información Confirmada a Partir del Código Fuente del Proyecto

  • CONFIRMADO Arquitectura Cliente-Servidor Desacoplada: Frontend en React 19 / Vite 7 y Backend independiente en Express 4.21 / Node.js con módulos ES nativos.
  • CONFIRMADO Motor de Persistencia: PostgreSQL 15+ administrado en Supabase con 51 migraciones SQL ejecutadas cronológicamente.
  • CONFIRMADO Gobernanza de Concurrencia: Implementación de la función almacenada registrar_movimiento_inventario con bloqueos a nivel de fila (FOR UPDATE) y restricción de stock no negativo.
  • CONFIRMADO Seguridad en Tiempo Real: Middleware de backend que comprueba el estado 'Activo' en base de datos en cada petición, impidiendo accesos rezagados por JWT.
  • CONFIRMADO Inteligencia Artificial y Pronósticos: Integración dual: Google Generative AI (Gemini Flash) para consultas operativas en lenguaje natural y Open-Meteo API para correlación de demanda climática.
  • CONFIRMADO Herramientas de Exportación: Generación de reportes de auditoría y facturación en formatos Excel (XLSX) y PDF (jsPDF).

13.2. Configuraciones Pendientes de Validar en el Entorno Final

  • PENDIENTE DE VERIFICACIÓN Alineación de Pruebas Unitarias del Chatbot: La prueba tests/chatbotRules.test.js espera la frase literal 'Reporte de Ventas Diario', requiriendo sincronizar la cadena devuelta por getFixedChatReply en el backend.
  • PENDIENTE DE VERIFICACIÓN Cuotas de Google Gemini en Producción: Validar el límite de peticiones por minuto (RPM) de la llave GEMINI_API_KEY en la consola de Google Cloud para prevenir errores 429 bajo tráfico elevado de operarios.
  • PENDIENTE DE VERIFICACIÓN Parámetros SMTP para Correos de Restablecimiento: Verificar si el servicio de correo de Supabase Auth utiliza el proveedor predeterminado o si se configurará un servidor SMTP transaccional dedicado (ej. SendGrid o Amazon SES).
  • PENDIENTE DE VERIFICACIÓN Hardware POS Específico: Comprobar los modelos exactos de impresoras térmicas de tickets (Epson TM-T20 o similares) y gavetas de dinero conectadas vía puerto RJ11/USB.
